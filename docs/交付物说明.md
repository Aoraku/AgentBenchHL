# 新游戏合作材料说明

一款游戏接入 AgentBench 与 AgentBench-HL，只需提交下面五类材料。不要求使用特定语言、框架或目录名；已有的比赛后端、SDK 和数据格式可以直接沿用，只要接口含义清楚、能够稳定运行。

## 1. 完整的游戏规则

规则文档应当让没有读过代码的人也能独立判断一场比赛是否合法。请说明玩家数量与角色、每名玩家能观察到的信息、回合或实时流程、地图与资源、随机机制、可执行操作、胜负与平局条件，以及超时、非法操作、中途退出等情况如何处理。若不同角色的观察或动作不对称，需要分别说明。

规则文档中的判定应与评测脚本一致；有歧义时，以文档中明确写出的规则为准。

## 2. 可运行的评测脚本

评测脚本负责启动选手、执行比赛、限制时间与资源、判定结果并生成回放。请提供一个稳定的命令行入口或函数入口，并写明依赖安装、选手接入方式、输入参数和输出位置。入口至少应能指定参赛选手、角色或座次以及随机种子；多人或非对称游戏应能覆盖需要评测的座次和角色组合。

评测结果需要以 JSON 或其他容易解析的格式给出比赛是否正常完成、胜负或得分、终局原因和回放路径。例如：

```json
{
  "status": "complete",
  "winner": "player_0",
  "scores": [1, 0],
  "rounds": 128,
  "replay": "replays/match-001.json"
}
```

字段名不作硬性要求，但必须区分“正常比赛中的失败、超时或非法操作”与“后端、进程或环境故障”。相同选手、角色和种子应能复现同一场比赛。若选手需要 SDK、通信协议或编译模板，请与评测脚本一并提供。

## 3. 尽可能多的人类选手

请尽可能多地提供能够通过同一评测入口运行的人类选手代码，用作功能测例、强度基准和 Elo 锚点。每名选手需要有稳定 ID、源码或可审计的构建材料、运行命令及依赖说明；非对称游戏应注明其支持的角色。

如有正式排行榜，请尽量一并提供，并保留选手名次、比赛分数、Elo、赛季或比赛版本等能够对应选手代码的信息。没有排行榜不影响接入；可以只提供已知的相对强弱，也不必人为补造分数。选手应尽量覆盖不同水平和不同策略风格，并说明代码可用于研究评测的授权范围。AgentBench-HL 会将人类选手代码与学习中的 Agent 隔离，Agent 只能看到允许公开的比赛结果与回放。

## 4. 评测回放 JSON 的说明

请提供至少一份真实、完整的回放 JSON，以及一份面向人的字段说明。说明中需要讲清每条记录发生在什么时刻、由谁行动、行动前后分别保存了什么状态、哪些操作被接受或拒绝、资源或得分如何变化，以及如何识别终局、胜者和终局原因。含隐藏信息的游戏还需标明哪些字段可以公开给选手或学习 Agent。

回放不要求改成统一结构。已有格式可以保留，但字段说明应足以让我们在不猜测游戏语义的情况下，把回放转换为自然语言时间线，并从任一决策点还原该玩家当时可见的状态、实际动作和直接结果。

## 5. 决策空间的定义

请按角色定义策略在一次决策中“看到什么、可以返回什么”。决策空间需要覆盖原子动作类型、参数范围、动作在不同状态下的合法条件、空操作，以及非法动作和超时的处理方式。若一次决策可以提交多个动作，还需说明动作顺序、组合规则和部分动作被拒绝时的语义。

定义可以使用文档、YAML、JSON Schema、类型声明或伪代码。建议同时给出稳定的动作表示，以及等价于 `legal_actions(state, player)` 的说明或实现，使框架能在同一公开状态上取得合法动作集合并记录策略实际选择。连续动作、文本动作或规模过大的动作空间，应说明用于比较两版策略的最小决策单位及其合法性检查方法。决策状态中不应混入随机种子、对手身份、回放编号或该玩家不可见的信息。

## 参考目录

下面只是一种便于交接的组织方式：

```text
game-name/
  README.md
  rules.md
  evaluator/
  players/
  replay_example.json
  replay_format.md
  decision_space.md
```

材料可采用其他结构。最低验收标准是：在干净环境中，按照 README 能用固定种子运行人类选手之间的比赛，得到可解析的结果和完整回放，并能从任一决策点确认公开观察、合法动作与实际动作。
